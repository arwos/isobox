# Работа с isobox

## Roadmap

- Перед выбором задачи читай `ROADMAP/ARCHITECTURE.md`, `TASK.md`, `CONTEXT.md`, `QA.md` соответствующей feature-группы и документы зависимостей.
- За один запрос выполняй ровно одну задачу, выбранную пользователем. Начинай её только при закрытых зависимостях; не расширяй scope на соседние задачи.
- После реализации обновляй статус задачи, технические решения в `CONTEXT.md` и фактически выполненные проверки в `QA.md`. Не отмечай незапущенные проверки успешными.
- Сохраняй согласованные границы безопасности: профиль валидируется до запуска; обязательные mounts, сетевые ограничения и лимиты применяются fail-closed. Не ослабляй их молча и не запускай приложение, если обязательное ограничение не удалось применить.

## Структура и команды

- Go CLI: `cmd/isobox/`; код — в `internal/cli`, `profile`, `preflight`, `sandbox`, `proxy`, `limits`, `integration`.
- Roadmap и критерии приёмки: `ROADMAP/`. Host/runtime runners и их предпосылки описаны в `tests/README.md`; список доступных сценариев — `./tests/run.sh --list`.
- `go.mod` задаёт модуль `github.com/arwos/isobox` и Go `1.26.8`. Форматируй изменённые Go-файлы через `gofmt -w <файлы>`.
- Из корня репозитория доступны `go build ./...`, `go test ./...` и `go vet ./...`; в QA для ограниченного окружения применялись `GOCACHE=/tmp/isobox-gocache GOMODCACHE=/tmp/isobox-gomodcache GOPATH=/tmp/isobox-gopath` перед командами Go.
- Makefile определяет `make build` (goppy), `make lint` (`goppy lint`), `make tests` (`goppy test`) и `make pre-commit` (устанавливает `goppy@latest`, затем license/lint/tests/build). Не запускай `make pre-commit` без необходимости: цель устанавливает latest tool и может менять файлы. CI workflow сейчас только настраивает Go и не содержит шагов сборки или тестов.
- Базовые сборка и тесты не заменяют runtime-приёмку. Запускай только релевантный runner из `tests/README.md`, от обычного пользователя, без `sudo`; сетевые, desktop, Podman и systemd/cgroup сценарии требуют перечисленных там возможностей. Отражай в `QA.md` реальные результаты и ограничения среды.

## Изменения и безопасность

- Сохраняй разделение: профиль описывает sandbox, команду приложения передаёт пользователь после `--`.
- Для сети и sandbox следуй действующим решениям `ROADMAP/ARCHITECTURE.md`, включая IPv4-only и fail-closed поведение; сначала проверь соответствующие зависимости и критерии приёмки.
- Не включай несвязанные пользовательские изменения в commit. Для реализации используй формат `<TASK-ID>: <краткое название>`.

## Сетевые контракты и документация

- README описывает `off`, `direct`, `proxy` и `egress` отдельными таблицами. При изменениях поведения сверяй эти таблицы с `ROADMAP/ARCHITECTURE.md`, сетевыми `TASK.md`, `CONTEXT.md` и реализацией.
- Сохраняй различия режимов: `off` закрывает исходящий трафик; `direct` использует rootless backend; `proxy` требует SOCKS5 alias и не делает direct fallback; `egress` применяет явный IPv4 allowlist. Proxy/egress TUN поддерживает только IPv4 TCP/UDP, не ICMP, raw IP или IPv6.
- Позиционные имя интерфейса и CIDR разрешены для `direct`, `proxy`, `egress`. Пользовательская сеть в `direct` требует совместимый pasta. В proxy/egress guest, DNS и gateway endpoints из заданной подсети должны оставаться различными и согласованными между `resolv.conf`, `/etc/hosts` и TUN policy.
- Egress upstream DNS требует allow-rule для IP DNS-сервера на порт 53. Встроенное имя `host.gateway.internal` разрешается в текущий виртуальный gateway; A обслуживается локально, AAAA и другие типы получают NODATA локально. Не добавляй DNS upstream-запрос для этого зарезервированного имени. Доступ к host loopback требует отдельного allow-rule на `127.0.0.1`, порт и протокол.
- При документационных изменениях выполняй `git diff --check`. Сборка, тесты и runtime acceptance подтверждают разные уровни поведения; указывай только реально выполненные проверки.

## Групповые сети

- Сверяй изменения сетевых групп с `ROADMAP/F09-network-groups/` и зависимостями F05, F06 и F08. Первым условием реализации является rootless-прототип; не вводи root/setuid helper и не ослабляй изоляцию без отдельного согласования.
- У каждой sandbox остаются отдельные network namespace и loopback. Повторяемые `group` подключают sandbox к нескольким сетям с отдельным IPv4 адресом в каждой; повторяемые `alias` и `app-id` публикуются в DNS каждой подключённой группы.
- Group DNS сначала отвечает по актуальным записям участников. Отсутствующее однословное имя (включая остановленный app-id/alias) получает локальный NXDOMAIN во всех режимах и не пересылается upstream; остальные неизвестные имена следуют DNS-политике режима. Ошибка manager или внешнего DNS upstream должна возвращать SERVFAIL по UDP и TCP, а не оставлять запрос без ответа.
- Явное членство разрешает внутригрупповой трафик также в `off`; исходящий трафик по-прежнему контролирует режим контейнера. Не допускай межгрупповой маршрутизации, обхода proxy/egress или доступа к host/LAN сверх действующих правил.
- Network manager и systemd user units должны проверять владельца/права состояния, конфликт подсетей/имён, активные подключения перед удалением и fail-closed поведение при потере manager или DNS.
