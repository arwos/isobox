# F06 Контекст

- Runtime-протокол — только SOCKS5; sing-box `v1.14.2` используется исключительно как тестовый server в rootless Podman. Fixture находится в `tests/f06-proxy/sing-box/`, использует loopback-only listener и локальные echo-сервисы; sing-box не является runtime-зависимостью.
- DNS для proxy mode выбирается по приоритету: упорядоченный список IPv4 DNS из профиля, общий DNS isobox, затем первый IPv4 resolver из host `/etc/resolv.conf`. Если у хоста нет IPv4 resolver и профиль/общие настройки его не задали, proxy-запуск блокируется. Список resolver-ов перебирается через SOCKS5 при ошибке предыдущего назначения; прямой DNS fallback отсутствует. Системное разрешение имени самого SOCKS-сервера остаётся необходимым для подключения к нему.
- По решению пользователя IPv6 полностью отключён namespace-local sysctl ещё до запуска приложения; proxy TUN также создаётся без IPv6 адресов и маршрутов. IPv6 packets в обработчике отбрасываются как дополнительная проверка.
- Proxy mode не передаёт bwrap флаги `--disable-userns` и `--assert-userns-disabled`, но этого недостаточно: bwrap `--dev` включает отдельную настройку `devpts`, из-за которой bwrap может перейти во второй user namespace уже после создания network namespace. Это следует из [исходника bubblewrap](https://github.com/containers/bubblewrap/blob/main/bubblewrap.c); Linux проверяет право записи сетевого sysctl по `CAP_NET_ADMIN` в user namespace-владельце network namespace ([исходник ядра](https://github.com/torvalds/linux/blob/master/net/sysctl_net.c)). В отчёте `/tmp/isobox-test-results/f06-proxy-runtime.1hUOS7/result.txt` был отказ `open .../disable_ipv6: permission denied`; после переноса создания сети helper применил sysctl, что подтвердили `/tmp/isobox-test-results/f06-proxy-runtime.A3k7cc/result.txt` и `/tmp/isobox-test-results/f06-proxy-runtime.E4RvCn/result.txt`. Последний отчёт показал две одинаковые строки `/proc/net/ipv6_route`: IPv6 null-discard entries ядра, а не маршруты с внешним next hop. Linux v6.12 определяет такую запись как `RTF_REJECT | RTF_NONEXTHOP`, с максимальной метрикой, типом unreachable и discard output ([исходник Linux v6.12](https://github.com/torvalds/linux/blob/v6.12/net/ipv6/route.c)). Поэтому helper допускает только точную zero-prefix/zero-next-hop запись с этими flags на `lo`; любые другие IPv6-маршруты блокируют запуск. Proxy не передаёт `--unshare-net`; доверенный helper создаёт network namespace после bwrap setup, уже в текущем user namespace, временно имея `CAP_SYS_ADMIN` и `CAP_NET_ADMIN`. Сразу после `unshare(CLONE_NEWNET)` helper сбрасывает `CAP_SYS_ADMIN`, оставляет только `CAP_NET_ADMIN` для IPv6/TUN и включает loopback. До `exec` приложения helper устанавливает namespace-blocking seccomp. Direct/off helper setup не меняется.
- Сетевой компонент isobox должен прозрачно перехватывать TCP и UDP. Обычное приложение не настраивает proxy и не получает credentials.
- SOCKS5 `CONNECT` и `UDP ASSOCIATE` описаны в [RFC 1928](https://www.rfc-editor.org/rfc/rfc1928.html). SOCKS5 не предоставляет IP-layer gateway для ICMP; сервер может молча отбросить неподдержанную UDP datagram.
- SOCKS5 username/password описан в [RFC 1929](https://www.rfc-editor.org/rfc/rfc1929); пароль передаётся открыто. Пользователь разрешил plain SOCKS5 с предупреждением. Сам SOCKS5 также не шифрует передаваемые данные.
- TUN читает/пишет IP packets через `/dev/net/tun`: [Linux kernel documentation](https://kernel.org/doc/html/latest/networking/tuntap.html). Наличие TUN и необходимые права проверяет F03.
- `slirp4netns --outbound-addr` не является proxy client; это binding outbound address/interface: [manual](https://github.com/rootless-containers/slirp4netns/blob/master/slirp4netns.1.md).
- TUN/IP stack для F06-T03: `gvisor.dev/gvisor v0.0.0-20260701204157-69c2d17aea96` (Apache-2.0; модуль требует Go 1.26.3, проект использует Go 1.26.8). Stack регистрирует только IPv4, TCP и UDP; собственный SOCKS5 protocol client остаётся компонентом isobox. Проверенные upstream API: [gVisor stack](https://github.com/google/gvisor/blob/69c2d17aea96/pkg/tcpip/stack/stack.go), [TCP forwarder](https://github.com/google/gvisor/blob/69c2d17aea96/pkg/tcpip/transport/tcp/forwarder.go), [UDP forwarder](https://github.com/google/gvisor/blob/69c2d17aea96/pkg/tcpip/transport/udp/forwarder.go), [channel endpoint](https://github.com/google/gvisor/blob/69c2d17aea96/pkg/tcpip/link/channel/channel.go), [module Go version](https://github.com/google/gvisor/blob/69c2d17aea96/go.mod).
- Официальный sing-box SOCKS inbound: https://sing-box.sagernet.org/configuration/inbound/socks/ . Он нужен для локальной проверки и не входит в runtime.
- Fixture использует официальный `ghcr.io/sagernet/sing-box:v1.14.2` image с тестовой auth-парой; config только для локальной проверки, `--network host` выбран для доступа сервера к привязанным на loopback TCP/UDP echo endpoints. Inbound bind также ограничен `127.0.0.1`. Проверка запуска/остановки сохраняется в `tests/f06-proxy/sing-box/run.sh`.

## F06-T05 — отдельный режим `egress`

Согласованные требования пользователя:

- Режим `proxy` остаётся внешним SOCKS5 и требует `proxy_alias`. Новый отдельный режим `egress` устанавливает исходящие соединения напрямую через сеть хоста только к адресам, разрешённым профилем. Он не скрывает внешний IP хоста.
- Proxy policy разрешает один или несколько IPv4 адресов/CIDR в одном `allow` блоке: `ip` может повторяться или задаваться списком. `port` задаёт список точных портов, а повторяемые позиционные записи `port_range START END;` — включительные диапазоны. `protocol` выбирает TCP/UDP. Если порты и протокол не заданы, правило разрешает все порты и оба протокола перечисленных адресов. Нет совпавшего правила — поток блокируется.
- Встроенный resolver сначала отвечает по статическим соответствиям домен → IPv4. UNIC задаёт запись блоком `record <domain> { ... }`, внутри которого повторяются значения `ip`; до 16 уникальных IPv4 на домен. Неизвестные имена последовательно отправляются на явно заданные `network.dns` upstream адреса до получения ответа; каждый адрес должен быть разрешён allowlist-ом на TCP/UDP port 53. Если upstream не задан или все адреса недоступны/запрещены, resolver отказывает. В `proxy` список DNS также проверяется по порядку через SOCKS5; если он пуст, сохраняется текущий host-resolver fallback. Статические записи доступны только в `egress`.
- Доступ к host loopback требуется через отдельный виртуальный gateway endpoint и явное allow-правило. Обычный `127.0.0.1` внутри sandbox остаётся loopback sandbox и сам по себе не проходит через TUN.

Реализационный контракт:

- Переиспользовать прозрачный TUN и host-side gVisor stack из F06-T03. Режим `egress` не требует SOCKS listener или proxy environment для приложения: policy проверяется на каждом TCP/UDP flow до host-side dial. Режим `proxy` с alias использует текущий SOCKS5 маршрут; если профиль также содержит allow rules, они фильтруют flows перед передачей SOCKS. Профиль с alias без allow rules сохраняет прежнее поведение.
- Upstream DNS в built-in режиме является упорядоченным списком обычных UDP/TCP flows к `network.dns`; каждый адрес требует подходящего allow-правила, включая порт 53. При ошибке предыдущего resolver пробуется следующий. Без `network.dns` host `/etc/resolv.conf` автоматически не используется.
- Host gateway — `10.89.0.3` в сети TUN `10.89.0.0/24`; `10.89.0.1` занят TUN, `10.89.0.2` — synthetic DNS endpoint. Policy handler распознаёт gateway destination и только после проверки правила на `127.0.0.1` и целевой порт соединяет его с host loopback. Обычный sandbox `127.0.0.1` остаётся локальным.
- Для статических записей в первой версии использовать точные домены и IPv4 A-записи; IPv6 остаётся отключённым. Доменная запись — только DNS mapping: разрешённый IP доступен приложению и при обращении по IP literal, и для других имён, ведущих на тот же IP.
- Все ошибки конфигурации проверяются до запуска; отсутствие правила, DNS upstream или исправного policy data plane не создаёт прямой обход. Таблица `isobox config` показывает режим, upstream, правила и статические записи.
- В `egress` журналировать неудачное DNS-разрешение (домен, qtype/transport и причину) и назначения, заблокированные allowlist (IP, порт, протокол и причину), в `~/.isobox/log/<app-id>.log`; пустой app-id использует `default`. Каталог создаётся с режимом `0700`, файл — `0600` и без symlink-follow. Если каталог или файл недоступны, предупредить через stderr и продолжить с закрытой по allowlist сетью; журнал не должен быть условием разрешения egress.

## F06-T01 — хранилище alias и credentials

- Команды управления: `isobox proxy add --alias=ALIAS --server=HOST:PORT [--auth=none|userpass]`, `isobox proxy list`, `isobox proxy remove --alias=ALIAS`. Credentials не принимаются в аргументах процесса; при `userpass` имя пользователя запрашивается с терминала, пароль вводится с отключённым echo. Прерывание сигнала восстанавливает настройки терминала.
- Файл хранится как `$XDG_CONFIG_HOME/isobox/proxies.unic`, либо `$HOME/.config/isobox/proxies.unic`, если `XDG_CONFIG_HOME` отсутствует или не абсолютен. Каталог `isobox` создаётся с точными правами `0700`, файл — `0600`, оба должны принадлежать текущему effective UID. Config-home должен принадлежать пользователю и не быть доступен группе/остальным на запись. Небезопасные права и symlink не исправляются автоматически: операция завершается ошибкой.
- Store использует версионированную UNIC-схему. Перед `unic.Unmarshal` проверяются неизвестные/повторные поля; ошибки декодирования не включают исходный текст, чтобы не вывести пароль. Записи сериализуются во временный файл, fsync-ятся и заменяются атомарно под directory lock. Ограничение размера — 1 MiB.
- Публичный API `internal/proxy` возвращает только alias, server и метод аутентификации. Чтение username/password находится в непубличном `loadRuntimeConfig` того же пакета для последующего SOCKS5 runtime; CLI `run` credentials не получает.
- Proxy-mode `run` проверяет alias и защищённость store до host preflight и печатает предупреждение, что SOCKS5 не шифрует credentials и трафик. Добавление proxy также выводит это предупреждение. SOCKS5 client подключён к прозрачному TUN data plane в F06-T03; live runtime acceptance остаётся открытой.
- Хост proxy принимается как IPv4 или DNS hostname и TCP port; IPv6 literal отклоняется в соответствии с IPv4-only контрактом isobox. SOCKS5 user/password ограничены 1–255 байтами без NUL, как требуется RFC 1929.

## F06-T03 — прозрачный proxy TUN

- Доверенный helper после bwrap setup создаёт собственный network namespace, принадлежащий текущему sandbox user namespace, и сразу сбрасывает временный `CAP_SYS_ADMIN`, сохраняя `CAP_NET_ADMIN` для сетевой настройки. Он отключает IPv6 namespace-local sysctl, включает loopback, затем создаёт `/dev/net/tun` с `IFF_TUN|IFF_NO_PI`, выставляет non-blocking mode, MTU 1500 и адрес `10.89.0.1/24`. Для `netlink.RouteAdd` default route задаётся явно как `0.0.0.0/0`; проверка после добавления принимает как nil destination, так и явный IPv4 zero-prefix route, но только через TUN link. Если профиль объявляет proxy ingress ports, установка main-table default route через TUN откладывается до готовности pasta: pasta временно добавляет default route на `isoboxp0`, helper удаляет его и устанавливает единственный default route через TUN до выпуска приложения из startup gate. До запуска приложения helper сбрасывает capability sets, выставляет `no_new_privs` и запрещает создание новых namespaces через seccomp.
- Приложение запускается после полного сброса capability sets. Helper передаёт TUN FD через owner-only Unix startup gate. Host проверяет `SO_PEERCRED`, связь peer с bwrap child, network namespace thread и результат `TUNGETIFF` (имя/режим интерфейса).
- Host-side stack использует gVisor `channel.Endpoint`, отдельные cancellable read/write workers и только IPv4/TCP/UDP protocol handlers. До инъекции отбрасываются пакеты, которые не являются IPv4 TCP/UDP; это также отбрасывает неожиданные IPv6, ICMP и прочие raw IP protocols. Пакетная очередь и flow count ограничены.
- TCP flow преобразуется в SOCKS5 `CONNECT`; каждый UDP flow использует отдельную SOCKS5 `UDP ASSOCIATE`. В sandbox resolver указывает внутренний адрес `10.89.0.2`, который направляется в TUN; сетевой модуль заменяет только назначения UDP/TCP port 53 на выбранный host resolver до SOCKS5 `UDP ASSOCIATE`/`CONNECT`. Это также обрабатывает host resolver на loopback, который иначе был бы отправлен в namespace `lo`. Alias/credentials и реальный DNS destination передаются только host-side сетевому компоненту, не helper argv, env или приложению. Перед выпуском startup gate проверяется TCP auth и создание UDP association; ошибка оставляет приложение заблокированным.
- Runtime probe проверяет DNS отрицательным запросом к зарезервированному `.invalid` имени. `EAI_NONAME` и `EAI_NODATA` являются допустимыми отрицательными результатами; временная ошибка разрешения и успешное разрешение такого имени проваливают probe.
- При завершении отменяется TUN reader, gVisor stack закрывает локальные endpoints, queue worker завершается, затем закрывается FD. Fatal ошибка data plane после запуска приводит к завершению sandbox; прямого fallback нет.
- Proxy mode с объявленными host port forwards использует pasta только как ingress transport. Требуются `--ns-ifname`, `--address`, `--netmask`, `--gateway` и остальные изоляционные флаги; pasta получает фиксированный `isoboxp0` с аргументами `--address=10.89.1.2 --netmask=24` (адрес `10.89.1.2/24`), gateway `10.89.1.1`, явные host forwards и `--no-splice`. `--address` pasta принимает только IP address, маска задаётся отдельным `--netmask`; CIDR в `--address` завершает startup ошибкой. Проверка настроенного адреса сравнивает host IP и prefix mask отдельно: `net.ParseCIDR` возвращает IP интерфейса отдельно от нормализованного адреса сети. Default route в ingress policy table задаётся явно как `0.0.0.0/0`, а проверка принимает как nil destination, так и IPv4 zero-prefix запись; при несовпадении helper выводит фактические маршруты этой таблицы. До выпуска приложения nftables разрешает исходящие пакеты через `isobox0` (SOCKS TUN) и ответы с conntrack mark на `isoboxp0`; новые прямые соединения блокируются. Trusted helper оставляет единственный default route через TUN и добавляет отдельный policy table/rule только для помеченных ответов. Отсутствующие флаги, nftables, интерфейс, route или rule блокируют запуск. Пользовательская runtime-приёмка DNS/TCP/UDP через SOCKS и marked TCP ingress прошла на Linux Mint 7; отчёт `/tmp/isobox-test-results/f06-proxy-runtime.3nZ7zT/result.txt`.
- В локальном Codex execution sandbox отсутствует `/dev/net/tun`, поэтому локальный runtime не мог проверить TUN. Пользовательская приёмка на Linux Mint 7 / kernel 6.12.116 / Podman 5.4.2 подтвердила startup gate, DNS/TCP/UDP через sing-box, published TCP ingress через pasta и штатный выход приложения: `/tmp/isobox-test-results/f06-proxy-runtime.3nZ7zT/result.txt`. Host-side packet capture и принудительное завершение SOCKS server после начала работы приложения этим runner не проверялись; direct fallback запрещён маршрутом через TUN, фильтром и lifecycle обработчиком fatal ошибки.

## F06-T02 — SOCKS5 TCP и UDP client

- Внутренний `socks5Client` создаётся из приватного `runtimeConfig`; наружу и в CLI credentials не передаются. Control connection всегда открывается как `tcp4` к сохранённому SOCKS server. Код не делает повторного direct dial при ошибке.
- Negotiation предлагает ровно один настроенный метод — no-auth либо username/password — и завершает соединение при несовпадении, отказе или некорректном ответе. Временный auth payload обнуляется после записи; ошибки не включают username/password.
- `CONNECT` кодирует только IPv4 и DNS hostname. `UDP ASSOCIATE` отправляет нулевой IPv4 endpoint, затем создаёт отдельный IPv4 UDP socket и передаёт датаграммы только адресу relay из SOCKS-ответа. Ответы принимаются только от relay endpoint; прочие источники отбрасываются.
- UDP association закрывает control connection и UDP socket при отмене context, закрытии или разрыве control connection. `FRAG != 0` не поддерживается и возвращает ошибку; IPv6 address type отклоняется. Успешный SOCKS reply с нулевым UDP relay port или relay без IPv4 адреса не запускает association.
- Имя назначения передаётся SOCKS-серверу как domain address, поэтому клиент не разрешает имена приложений локально. Если SOCKS-сервер вернул domain в BND.ADDR UDP relay, клиент разрешает только этот адрес через системный IPv4 resolver, чтобы достичь самого relay; TUN/DNS data plane и правила DNS для приложения остаются предметом F06-T03.
- Уровень F06-T02 проверяется с in-process SOCKS peer и UDP socket mock. Реальный TUN, IPv6/ICMP/raw packet rejection и sing-box/Podman acceptance относятся к F06-T03/T04 и этими unit checks не подтверждаются.
