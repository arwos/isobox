# F02 Контекст

- Формат конфигурации — UNIC из `go.osspkg.com/unic`; профиль задаёт sandbox, но не команду приложения.
- Значения по умолчанию пользователь переопределяет профилем; общий DNS может быть переопределён профилем.
- Безопасное значение по умолчанию для сети — `off`.
- Требуется типизированная Go-структура и последующая прикладная валидация, а не только успешный decode.
- Доступная инструкция по UNIC — `/home/user/.agents/skills/osspkg/osspkg-lib-unic-usage/SKILL.md`. Проверены `go.osspkg.com/unic` v1.0.2 и его исходники: `unic.Unmarshal(data, &cfg)` декодирует в переданную структуру; неизвестные поля внутри struct пропускаются, дубли одиночных полей decoder отклоняет, slices допускают повторные поля.
- Зависимость закреплена в `go.mod` как `go.osspkg.com/unic v1.0.2`; транзитивная `go.osspkg.com/bb v1.0.1` закреплена в `go.sum`.
- В `internal/profile/schema.go` определены Profile и Settings с `unic` tags. Профиль не содержит app command. Профильный пустой network mode означает inherit; built-in Settings default — `off`.
- Общий DNS хранится в Settings и может быть переопределён в профиле. Настроенное значение должно быть IPv4/IPv6 адресом без порта. В `proxy` mode требуется эффективный DNS из профиля или Settings, чтобы дальнейший сетевой компонент не мог незаметно перейти на host DNS. В `direct` mode пустой DNS допускается, потому что режим прямо разрешает обычную сеть.
- PortRule требует host address и описывает одиночный порт через `port` либо inclusive range через `port` + `end_port`; host и sandbox port одинаковы. Это низкорисковое допущение: пользователь отдельно не задавал перенумерацию портов.
- Лимиты типизированы явными единицами: `cpu_quota_percent` (100 = один логический CPU), `memory_bytes`, `process_count`, `open_files`; ноль означает отсутствие запроса лимита.
- GUI grants по умолчанию выключены; writable mounts требуют явного `read_only=false`, по умолчанию mount read-only.
- `DecodeProfile` и `DecodeSettings` сначала проверяют UNIC-поля по схеме из struct tags, затем вызывают go-unic, затем запускают прикладную валидацию. Так неизвестное security-поле не игнорируется decoder. Проверка ограничивает документ 1 MiB и вложенность 64 уровнями, принимает UTF-8/BOM, комментарии, кавычки, тройные backticks, блоки, списки и maps.
- Валидация проверяет версию; нормализованные абсолютные пути; запрещает root как HOME/mount source/target; требует source/target для каждого mount; обнаруживает повторные mount targets, некорректные network modes, IP DNS/bind addresses, proxy alias и proxy DNS, неверные порты/диапазоны/протоколы и пересекающиеся опубликованные порты. Проверка путей синтаксическая: существование и пригодность host mount source проверит preflight при запуске.
- `ResolveProfile` материализует эффективный network mode и DNS. Пустой профильный mode наследует Settings, built-in mode — `off`; профильный DNS перекрывает общий. CLI уже читает и валидирует профиль до отказа от запуска, а пока передаёт только built-in settings; загрузка пользовательского файла Settings будет подключена вместе с конфигурационным хранилищем.
- Для `proxy` alias и DNS обязательны в итоговой конфигурации. Alias допускается при отсутствующем profile mode, чтобы задать его для унаследованного proxy default. Alias вместе с явным `off`/`direct` отклоняется как конфликт.
