# F09 — Именованные групповые сети

## Зависимости

- Требует: F02, F04, F05-T03, F06-T05 и F08-T02.
- F09-T01 — rootless feasibility spike; может выполняться после F04, не ожидая runtime-приёмки F05-T03 и F06-T05.
- F09-T02 требует F09-T01 и F08-T02. Подключение sandbox и режимов в F09-T03—T05 начинается только после закрытия F05-T03 и F06-T05.

## Задачи

- [ ] F09-T01 — Доказать rootless-модель общей bridge-сети.
  - Шаги: проверить, как сохранить общий владеющий user namespace и bridge между запусками, создавая отдельный network namespace для каждого sandbox; проверить `veth`/маршрутизацию и передачу namespace FD в bubblewrap; проверить отключение namespace-операций и сброс capabilities приложения.
  - Приёмка: обычный пользователь без `sudo`, root/setuid helper создаёт изолированную сеть с как минимум двумя отдельными network namespaces, каждый со своим loopback и уникальным IP, которые обмениваются IPv4 TCP/UDP внутри группы; host/LAN и сети вне группы недоступны без заданного внешнего режима. Записать выбранную модель владельца namespace, security границы, совместимость с поддерживаемыми bwrap и kernel; если это нельзя доказать, зависимые задачи остаются заблокированы до выбора альтернативы.

- [ ] F09-T02 — Управлять постоянной сетью через пользовательский systemd.
  - Шаги: добавить `isobox network create --name=NAME --subnet=IPv4-CIDR`, `list` и `remove`; хранить описание сети в приватном `~/.isobox`; создавать, запускать и включать user unit для каждой именованной сети; проверять сеть и состояние manager до операций.
  - Приёмка: созданная сеть и bridge остаются активными без подключённых sandbox и автоматически восстанавливаются, когда запускается пользовательский systemd manager; `remove` останавливает и удаляет только unit/данные isobox и отказывает при активных участниках; сеть и файлы пользователя не перезаписываются, ошибки manager не приводят к запуску sandbox с неподключённой сетью. Документировать, что запуск user manager до login требует включённого lingering; isobox не включает его автоматически.

- [ ] F09-T03 — Подключать sandbox к нескольким группам с уникальной адресацией.
  - Шаги: расширить профиль повторяемыми `group NAME` и `alias NAME`; на каждую группу подключать отдельный интерфейс/veth и выделять уникальный IPv4 адрес из её CIDR; регистрировать и очищать членство атомарно с жизненным циклом sandbox.
  - Приёмка: одна sandbox имеет отдельный IP в каждой назначенной группе и отдельный loopback; адреса участников внутри группы не конфликтуют; неизвестная группа, исчерпанный пул, пересекающиеся CIDR у групп одного sandbox или ошибка подключения блокируют запуск до открытия gate; выход/аварийный выход sandbox освобождает lease и интерфейс.

- [ ] F09-T04 — Разрешать участников по DNS-имени внутри каждой группы.
  - Шаги: обслуживать записи активных членов каждой сети; публиковать их `app-id` и все повторяемые aliases во всех подключённых группах; обновлять DNS при подключении, отключении и смене состояния manager.
  - Приёмка: участники разрешают друг другу IP-адрес, app-id и каждый alias; имена видны только в общей группе; конфликт имён в группе, испорченная DNS-конфигурация или несогласованное состояние membership не запускают sandbox с некорректной регистрацией; после отключения старые записи перестают разрешаться.

- [ ] F09-T05 — Сохранить внешнюю сетевую политику при межконтейнерной связи.
  - Шаги: подключить групповые маршруты к `off`, `direct`, `proxy` и `egress`; разрешить через интерфейсы группы только внутригрупповые назначения; не менять внешний маршрут каждого режима и запретить межгрупповую маршрутизацию.
  - Приёмка: `off` может обмениваться трафиком с участниками назначенных групп, но не с host, LAN или Интернетом; `direct` сохраняет собственный IPv4 egress, `proxy` не получает direct fallback, `egress` сохраняет allowlist для внешних назначений; трафик к группе не уходит через внешний TUN/провайдер; неподключённые группы и host loopback остаются закрыты. Проверить на обычном Linux-пользователе минимум две группы, несколько сетевых режимов, рестарт manager и cleanup.
