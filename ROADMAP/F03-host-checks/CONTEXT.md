# F03 Контекст

- Поддерживаемая базовая конфигурация: `bwrap`, `pasta` или `slirp4netns`, включённые пользовательские namespace. isobox не устанавливает пакеты и не меняет sysctl автоматически.
- Proxy mode дополнительно зависит от доступа к `/dev/net/tun` и возможности создать TUN-интерфейс; kernel docs указывают, что создание/подключение интерфейса требует соответствующего `CAP_NET_ADMIN` в сетевом namespace.
- `pasta` и `slirp4netns` — разные rootless backend. Автовыбор: pasta, затем slirp только после проверки эквивалентности требуемых гарантий.
- Источники: [bubblewrap](https://github.com/containers/bubblewrap/blob/main/README.md), [pasta manual](https://passt.top/builds/latest/web/passt.1.html), [slirp4netns manual](https://github.com/rootless-containers/slirp4netns/blob/master/slirp4netns.1.md), [Linux TUN/TAP](https://kernel.org/doc/html/latest/networking/tuntap.html).
- Доступность TUN и cgroup/systemd-механизмов различается между дистрибутивами; запуск при отсутствии нужной возможности закрывается ошибкой с remediation.
- Bubblewrap требует user namespace при rootless запуске; опция `--unshare-user` делает требование явным, а `--unshare-net` проверяет доступность отдельного network namespace. Это подтверждено официальными [bwrap README](https://github.com/containers/bubblewrap/blob/main/README.md) и [bwrap man page](https://github.com/containers/bubblewrap/blob/main/bwrap.xml).
- Проверка user namespace запускает дочерний процесс isobox с `CLONE_NEWUSER` и отображением текущих uid/gid на namespace uid/gid 0. Она не меняет sysctl и не использует root fallback.
- `internal/preflight.Check` проверяет Linux, `bwrap --version`, минимальный реальный rootless bwrap с `/bin/true`, user namespace и наличие `pasta` или `slirp4netns`; найденные пути и выбранный network plan возвращаются вызывающему коду. Правила выбора записаны в F03-T02 ниже.
- Для `proxy` отдельный дочерний процесс создаёт user+network namespace, открывает `/dev/net/tun` и выполняет `TUNSETIFF` для временного TUN. Закрытие fd очищает интерфейс. Это проверяет одновременно device access и kernel permission в namespace, без изменения host network.
- Пока F07 не реализован, любое ненулевое CPU/memory/process/open-files ограничение fail-closed блокирует запуск с перечнем неподдержанных полей. Запрос ограничения не считается проверенным или применённым по одному лишь наличию sysctl/cgroup controller.
- F03-T02 дополнил preflight запуском `pasta --help` и `slirp4netns --help` с таймаутом и выбором backend по реально объявленным long options. `pasta` выбирается первым только при наличии `--config-net`, `--tcp-ports`, `--udp-ports`, `--tcp-ns`, `--udp-ns`; runtime обязан выставить для не объявленных направлений `none`, потому что у pasta авто-forwarding включён по умолчанию. Если pasta отсутствует или не может обеспечить явно заданную семантику, разрешён проверенный fallback на slirp.
- Для `slirp4netns` preflight требует `--configure`, `--enable-ipv6`, `--ready-fd`, `--exit-fd`, а при публикации портов — `--api-socket`. IPv6 host bind address не допускает fallback: официальный API host forwarding принимает IPv4 и отдельный порт на вызов, поэтому реализация API должна развернуть диапазон в отдельные запросы. Profile DNS override передаётся через контейнерный `resolv.conf`; без override используется внутренний DNS endpoint slirp.
- DNS-адрес профиля передаётся в `BackendSelection`; пустой адрес помечен `UseHostDNS`. Последующая сборка сети должна создать корректный контейнерный `resolv.conf`, не копируя недоступный loopback resolver хоста напрямую. Для slirp без override используется его внутренний DNS endpoint; для pasta runtime передаёт resolver из host DNS settings. DNS/порты считаются готовыми только после запуска helper и подтверждения их настройки.
- `off` без опубликованных портов выбирает backend `none`. `off` с портами блокируется до появления проверяемого egress-фильтра: одного pasta/slirp forwarding недостаточно для гарантии «только ответы на подключения хоста». `proxy` выбирает собственный TUN backend, но пока блокируется при published ports, поскольку комбинированный ingress path появится в F05/F06. Это fail-closed ограничения до соответствующих задач.
- Реальный bind host address и успешное применение port rules можно подтвердить только runtime helper; preflight выбирает совместимый API, а будущий runtime не должен стартовать приложение, пока все объявления не применены. Ошибка bind/API должна завершать весь запуск.
- Проверенные официальные сведения: [pasta manual](https://passt.top/builds/latest/web/passt.1.html) указывает `auto` по умолчанию для `-t/-u` и `-T/-U`, IPv4/IPv6 адреса и формат ranges; [slirp4netns manual](https://github.com/rootless-containers/slirp4netns/blob/master/slirp4netns.1.md) документирует IPv6 как experimental, API socket и DNS redirect. Его [официальный API source](https://raw.githubusercontent.com/rootless-containers/slirp4netns/master/api.c) принимает TCP и UDP, но использует `AF_INET` и один порт на запрос.
- Текущая среда: `bwrap`, `pasta`, `slirp4netns` находятся в `PATH`; `/dev/net/tun` отсутствует. Наличие бинарников не доказывает, что namespace-пробы пройдут на любой целевой системе.
