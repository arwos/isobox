# F05 Контекст

- Согласованные режимы: `off`, `direct`, `proxy`.
- В `off` приложение не инициирует сетевые запросы в Интернет, LAN или на хост; входящие от хоста соединения к объявленным портам разрешены вместе с ответами на них.
- Портовое правило требует host bind address; протокол TCP/UDP задаётся отдельно либо оба при пропуске; разрешены одиночный порт и диапазон.
- pasta имеет auto port-forward defaults для TCP/UDP. isobox должен явно отключать автоматическое пробрасывание и перечислять только профильные правила.
- slirp4netns API host forwarding — IPv4 only; если профиль просит IPv6 или нужную семантику, slirp не является допустимым fallback.
- `slirp4netns --outbound-addr` означает адрес/интерфейс исходящих сокетов, не URL прокси.
- Источники: [pasta manual](https://passt.top/builds/latest/web/passt.1.html), [slirp4netns manual](https://github.com/rootless-containers/slirp4netns/blob/master/slirp4netns.1.md).
- Критический инженерный риск: сочетание «входящие опубликованные порты + отсутствие любого исходящего обхода» нельзя считать выполненным только потому, что создан network namespace. Оно требует отдельного доказательства и негативных проверок egress.
- Реализация `off` с портами: выбран только pasta. Передача host-to-namespace использует явные `--tcp-ports`/`--udp-ports`, `--tcp-ns=none`/`--udp-ns=none`, `--no-icmp` и `--no-splice`; последнее важно, потому что pasta иначе может провести локальный forwarding в обход tap. Когда правило содержит только TCP или только UDP, второй handler отключается через `--no-udp`/`--no-tcp`. slirp fallback пока отвергается: эквивалентность его API-forwarding с фильтром не подтверждена.
- Режиму `off` без опубликованных портов не нужен сетевой backend; preflight требует pasta и nftables только при явных host forwards.
- `direct` использует `pasta --config-net` или fallback `slirp4netns --configure --enable-ipv6`; приложение удерживается bwrap `--block-fd` до готовности сетевого процесса. Pasta пишет PID-файл после инициализации; isobox сверяет PID и, если procfs permissions позволяют, дополнительно проверяет ownership ожидаемых host sockets. Для `off` с портами используется тот же readiness handshake. Slirp сигнализирует через `ready-fd`, а профильные host forwards добавляются через API до release gate.
- `direct` отключает автоматические host публикации в обоих направлениях. Pasta получает `--tcp-ns=none`/`--udp-ns=none` и отдельные `--tcp-ports`/`--udp-ports`; slirp не открывает host forwards до явных `add_hostfwd` запросов. API slirp принимает IPv4 host address и один порт на запрос, поэтому диапазоны разворачиваются в последовательность запросов; ошибка любого правила отменяет запуск.
- Direct DNS содержится в read-only `/etc/resolv.conf`, созданном через bwrap `--ro-bind-data`. Для pasta host-loopback resolvers переводятся в `--dns-forward`/`--dns-host`; для slirp используется встроенный `10.0.2.3`, если DNS не переопределён профилем. Источники: [pasta manual](https://passt.top/builds/latest/web/passt.1.html), [slirp4netns API/manual](https://github.com/rootless-containers/slirp4netns/blob/master/slirp4netns.1.md).
- PID-файл pasta — обязательный readiness сигнал; без него gate не открывается. Если доступны `/proc/<pid>/fd` и `/proc/<pid>/net`, isobox дополнительно сопоставляет endpoint-ы с сокетами pasta и учитывает native endianness Linux ABI. Slirp port rules разворачиваются в отдельные запросы `add_hostfwd`; их сериализация и fail-closed разбор API-ответа покрыты unit-тестами. Реальный slirp API socket и TCP/UDP host-forward путь проверены live acceptance harness.
- Egress guard: проверенный в preflight абсолютный путь к `nft` передаётся helper-процессу; он создаёт таблицу `inet isobox` внутри новой network namespace до запуска приложения. Вход и output имеют `policy drop`; loopback и established разрешены, новые входящие TCP/UDP — только на указанные профильные порты. Forward policy — drop. Если nft не применяет полный набор правил, helper завершается до запуска приложения.
- Порядок полномочий: для этого короткого шага bwrap добавляет только `CAP_NET_ADMIN` helper-процессу в user namespace, которая владеет network namespace. После применения правил helper включает `no_new_privs`, сбрасывает capability sets, устанавливает seccomp-ограничение на namespace syscalls и только затем выполняет приложение. Для профилей без опубликованных портов bwrap напрямую использует `--disable-userns` и `--assert-userns-disabled`.
- Стартовый барьер: bwrap сообщает PID namespace-процесса и ждёт на `--block-fd`; pasta подключается к нему от того же обычного пользователя. isobox ждёт PID-файл pasta, сверяет его PID с запущенным процессом и при доступном procfs подтверждает ownership ожидаемых host-сокетов. Если handshake или доступная проверка сокетов не проходит за восемь секунд, bwrap и pasta завершаются без запуска приложения. При неожиданном выходе pasta работа приложения прекращается.
- Для off+ports требуется установленный `nft`; его бинарный файл должен быть доступен в стандартном rootfs, который подключает isobox. Правила строятся только из проверенных числовых портов; host bind address применяется только в аргументах pasta.
- Seccomp сейчас принимает native ABI amd64, arm64, 386, arm, ppc64/ppc64le, s390x и riscv64. Для другого Linux ABI запуск off+ports блокируется. `clone3` возвращает `ENOSYS`, чтобы runtime при наличии fallback мог использовать `clone`; совместимость приложений без такого fallback требует runtime acceptance.
- Live acceptance для `off` без портов подтвердила отказ host-loopback TCP, внешних TCP/UDP и DNS. Для `off` с портами установленный pasta проходит capability preflight, а запуск доходит до nft helper; в текущем ограниченном окружении `nft` завершается с `netlink: Error: cache initialization failed: Operation not permitted`, после чего приложение не стартует. Поэтому nft guard, ingress и ответы на входящие соединения пока не считаются принятыми.
- Live acceptance для direct через slirp4netns 1.2.1 подтвердила default DNS, profile DNS override, внешний IPv4 TCP/UDP, полный TCP/UDP forwarding диапазон, bind на точный loopback адрес и отказ на не объявленном порту. Pasta capability options проверяются parser probes, потому что `pasta --help` обрезан на 4096 байтах; runtime сравнение pasta/slirp пока не выполнено. Внешний IPv6 не проверялся, потому что на host нет IPv6 default route. Проверяемые сценарии сохранены в `source/slirp_acceptance.py` и `source/pasta_off_acceptance.py`; результаты и ограничения — в `QA.md`.
- Runtime сравнение pasta/slirp, внешний IPv6 и off-mode firewall/ingress acceptance остаются открыты. Статическая сборка и slirp acceptance не доказывают эти свойства.
- Дополнительный источник для startup gate и capabilities: [bubblewrap manual](https://github.com/containers/bubblewrap/blob/main/bwrap.xml).
