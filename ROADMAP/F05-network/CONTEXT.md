# F05 Контекст

- Согласованные режимы: `off`, `direct`, `proxy`.
- В `off` приложение не инициирует сетевые запросы в Интернет, LAN или на хост; входящие от хоста соединения к объявленным портам разрешены вместе с ответами на них.
- Портовое правило требует host bind address; протокол TCP/UDP задаётся отдельно либо оба при пропуске; разрешены одиночный порт и диапазон.
- pasta имеет auto port-forward defaults для TCP/UDP. isobox должен явно отключать автоматическое пробрасывание и перечислять только профильные правила.
- slirp4netns API host forwarding — IPv4 only; если профиль просит IPv6 или нужную семантику, slirp не является допустимым fallback.
- `slirp4netns --outbound-addr` означает адрес/интерфейс исходящих сокетов, не URL прокси.
- Источники: [pasta manual](https://passt.top/builds/latest/web/passt.1.html), [slirp4netns manual](https://github.com/rootless-containers/slirp4netns/blob/master/slirp4netns.1.md).
- Критический инженерный риск: сочетание «входящие опубликованные порты + отсутствие любого исходящего обхода» нельзя считать выполненным только потому, что создан network namespace. Оно требует отдельного доказательства и негативных проверок egress.
- Реализация `off` с портами: выбран только pasta. Передача host-to-namespace использует явные `--tcp-ports`/`--udp-ports`, `--tcp-ns=none`/`--udp-ns=none`, `--no-icmp` и `--no-splice`; последнее важно, потому что pasta иначе может провести локальный forwarding в обход tap. Когда правило содержит только TCP или только UDP, второй handler отключается через `--no-udp`/`--no-tcp`. slirp fallback пока отвергается: эквивалентность его API-forwarding с фильтром не подтверждена.
- Режиму `off` без опубликованных портов не нужен сетевой backend; preflight требует pasta и nftables только при явных host forwards.
- `direct` использует `pasta --config-net` или fallback `slirp4netns --configure --enable-ipv6`; приложение удерживается bwrap `--block-fd` до готовности сетевого процесса. Pasta пишет PID-файл после инициализации; isobox сверяет PID и, если procfs permissions позволяют, дополнительно проверяет ownership ожидаемых host sockets. Для `off` с портами helper создаёт network namespace после bwrap mounts, устанавливает фильтр и сообщает готовность через временный Unix socket. Supervisor находит host TID потока с новым netns, подключает pasta и выпускает helper только после pasta readiness. Slirp сигнализирует через `ready-fd`, а профильные host forwards добавляются через API до release gate.
- `pasta` выбирает IPv6-интерфейс по host routes: без default route он может выбрать interface, если маршрут есть только на одном. На проверенном host default route отсутствует, а link-local routes есть на `tun0` и `wlp3s0`; явный `::1` host-forward не готовится до запуска приложения. Acceptance harness проверяет TCP+UDP bind на `::1`, когда host route selection доступна; внешние IPv6 DNS/TCP/UDP проверяются только при default route. Источник: [pasta manual](https://passt.top/builds/latest/web/passt.1.html).
- Если совместимый pasta выбран, но его setup завершается ошибкой до release gate, direct mode пробует заранее проверенный slirp backend. Переход разрешён только при поддержке IPv4 host forwards и совместимого DNS; loopback DNS override и IPv6 host bind блокируют этот fallback. Pasta сначала останавливается, чтобы освободить созданные им host sockets. Если slirp тоже не готов, запуск остаётся fail-closed; после старта приложения backend не меняется.
- Resolver для такого fallback монтируется read-only с адресами обоих backend. Одинаковые адреса дедуплицируются; при разных адресах fallback nameserver включается после primary, с `timeout:1 attempts:1`, чтобы приложению не требовалось перемонтировать resolver после выбора backend.
- `direct` отключает автоматические host публикации в обоих направлениях. Pasta получает `--tcp-ns=none`/`--udp-ns=none` и отдельные `--tcp-ports`/`--udp-ports`; slirp не открывает host forwards до явных `add_hostfwd` запросов. API slirp принимает IPv4 host address и один порт на запрос, поэтому диапазоны разворачиваются в последовательность запросов; ошибка любого правила отменяет запуск.
- Direct DNS содержится в read-only `/etc/resolv.conf`, созданном через bwrap `--ro-bind-data`. Для pasta host-loopback resolvers переводятся в `--dns-forward`/`--dns-host`; для slirp используется встроенный `10.0.2.3`, если DNS не переопределён профилем. Источники: [pasta manual](https://passt.top/builds/latest/web/passt.1.html), [slirp4netns API/manual](https://github.com/rootless-containers/slirp4netns/blob/master/slirp4netns.1.md).
- PID-файл pasta — обязательный readiness сигнал; без него gate не открывается. Если доступны `/proc/<pid>/fd` и `/proc/<pid>/net`, isobox дополнительно сопоставляет endpoint-ы с сокетами pasta и учитывает native endianness Linux ABI. Slirp port rules разворачиваются в отдельные запросы `add_hostfwd`; их сериализация и fail-closed разбор API-ответа покрыты unit-тестами. Реальный slirp API socket и TCP/UDP host-forward путь проверены live acceptance harness.
- Egress guard: проверенный в preflight абсолютный путь к `nft` передаётся helper-процессу; он создаёт таблицу `inet isobox` внутри новой network namespace до запуска приложения. Вход и output имеют `policy drop`; loopback и established разрешены, новые входящие TCP/UDP — только на указанные профильные порты. Forward policy — drop. Если nft не применяет полный набор правил, helper завершается до запуска приложения.
- Порядок полномочий: bwrap даёт helper-у `CAP_SYS_ADMIN` и `CAP_NET_ADMIN` только внутри rootless user namespace. Helper устанавливает `no_new_privs`, создаёт новый network namespace, сбрасывает `CAP_SYS_ADMIN`, передаёт `CAP_NET_ADMIN` только процессу nft, после применения правил сбрасывает все capability sets и устанавливает seccomp-ограничение на namespace syscalls. Приложение запускается без capabilities. Для профилей без опубликованных портов bwrap напрямую использует `--disable-userns` и `--assert-userns-disabled`.
- Стартовый барьер: `direct` использует bwrap `--block-fd`; off+ports helper ждёт на временном Unix socket, смонтированном read-only в `/run`. Supervisor проверяет peer credentials, находит host TID потока в изолированном netns, затем подключает pasta. Pasta пишет PID-файл после инициализации; isobox сверяет PID и при доступном procfs подтверждает ownership ожидаемых host-сокетов. При ошибке helper, pasta или startup gate приложение не запускается; при неожиданном выходе pasta работа приложения прекращается.
- Для off+ports требуется установленный `nft`; его бинарный файл должен быть доступен в стандартном rootfs, который подключает isobox. Правила строятся только из проверенных числовых портов; host bind address применяется только в аргументах pasta.
- Seccomp сейчас принимает native ABI amd64, arm64, 386, arm, ppc64/ppc64le, s390x и riscv64. Для другого Linux ABI запуск off+ports блокируется. `clone3` возвращает `ENOSYS`, чтобы runtime при наличии fallback мог использовать `clone`; совместимость приложений без такого fallback требует runtime acceptance.
- Live acceptance для `off` без портов подтвердила отказ host-loopback TCP, внешних TCP/UDP и DNS. Итоговая `pasta_off_acceptance.py` для `off` с портами подтвердила блокировку host/Internet TCP, UDP/DNS, невозможность создать ICMP datagram socket, работу host TCP/UDP на объявленном порту и отказ на не объявленном порту. Ранние nft/pasta failures и их причины описаны в `QA.md`; они устранены поздним созданием network namespace после bwrap mounts.
- `pasta --help` обрезан на 4096 байтах, поэтому скрытые capability flags проверяются parser probes. Актуальная runtime-проверка direct IPv4 на pasta и slirp, включая общий портовый набор, DNS override и injected startup fallback, прошла; внешний IPv6 не проверялся, потому что на host нет IPv6 default route. Сценарии сохранены в `source/slirp_acceptance.py`; off-mode port acceptance — в `source/pasta_off_acceptance.py`.
- Direct runtime fallback между pasta/slirp проверяет только заранее подтверждённо совместимые профили. Profile DNS loopback и IPv6 host forwarding не получают slirp fallback из-за различной адресной семантики/API.
- Runtime сравнение pasta/slirp для IPv4 и off-mode firewall/ingress acceptance подтверждены. Внешняя IPv6-приёмка для direct остаётся открыта: у host нет IPv6 default route. Статические проверки не заменяют этот runtime-сценарий.
- Дополнительный источник для startup gate и capabilities: [bubblewrap manual](https://github.com/containers/bubblewrap/blob/main/bwrap.xml).
