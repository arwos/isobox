# F05 Контекст

- Согласованные режимы: `off`, `direct`, `proxy`.
- По решению пользователя сеть isobox полностью IPv4-only. Профильные DNS и host bind адреса должны быть IPv4. Перед запуском приложения trusted helper в каждом network namespace выставляет `net.ipv6.conf.default.disable_ipv6=1` и `net.ipv6.conf.all.disable_ipv6=1`, проверяет пустой `/proc/net/if_inet6`, сбрасывает capabilities и оставляет `no_new_privs=1`.
- В `off` приложение не инициирует сетевые запросы в Интернет, LAN или на хост; входящие от хоста соединения к объявленным портам разрешены вместе с ответами на них.
- Портовая запись имеет вид `port <IPv4 bind address> <port> [protocol [end_port]];`. Протокол TCP/UDP задаётся третьим значением, по умолчанию используются оба; четвёртое значение задаёт включительный конец диапазона.
- Profile `network.dns` можно указывать повторно; адреса используются по порядку как DNS upstream-ы. Этот список заменяет одиночный global `settings.defaults.dns`.
- pasta имеет auto port-forward defaults для TCP/UDP. isobox должен явно отключать автоматическое пробрасывание и перечислять только профильные правила.
- slirp4netns API host forwarding — IPv4 only. Его запуск не получает `--enable-ipv6`; pasta запускается с `--ipv4-only`. Если backend не может подтвердить IPv4-only конфигурацию, запуск блокируется.
- `slirp4netns --outbound-addr` означает адрес/интерфейс исходящих сокетов, не URL прокси.
- Источники: [pasta manual](https://passt.top/builds/latest/web/passt.1.html), [slirp4netns manual](https://github.com/rootless-containers/slirp4netns/blob/master/slirp4netns.1.md).
- Критический инженерный риск: сочетание «входящие опубликованные порты + отсутствие любого исходящего обхода» нельзя считать выполненным только потому, что создан network namespace. Оно требует отдельного доказательства и негативных проверок egress.
- Реализация `off` с портами: выбран только pasta. Передача host-to-namespace использует явные `--tcp-ports`/`--udp-ports`, `--tcp-ns=none`/`--udp-ns=none`, `--no-icmp` и `--no-splice`; последнее важно, потому что pasta иначе может провести локальный forwarding в обход tap. Когда правило содержит только TCP или только UDP, второй handler отключается через `--no-udp`/`--no-tcp`. slirp fallback пока отвергается: эквивалентность его API-forwarding с фильтром не подтверждена.
- Режиму `off` без опубликованных портов не нужен сетевой backend; preflight требует pasta и nftables только при явных host forwards.
- `direct` и `off` без портов создают network namespace в trusted helper-е после bwrap mounts. Для direct supervisor ждёт Unix-socket readiness, находит host TID в новом netns, запускает pasta/slirp и выпускает helper только после готовности backend и forwards. Helper устанавливает IPv6 sysctl, затем до `exec` сбрасывает capabilities. Pasta пишет PID-файл, который isobox сверяет; slirp сигнализирует через `ready-fd`, а профильные forwards добавляются API-запросами до release gate. Для `off` с портами helper дополнительно устанавливает nftables default-drop до публикации портов.
- IPv6 acceptance не зависит от host routes: приложение должно видеть пустой `/proc/net/if_inet6` (в том числе без `::1`) и не иметь effective/permitted/inheritable/ambient capabilities; `NoNewPrivs` должен быть 1. Pasta дополнительно работает с `--ipv4-only`; slirp запускается без `--enable-ipv6`. Linux kernel docs подтверждают, что `conf/all/disable_ipv6` меняет все interface настройки, удаляет адреса/routes, а `conf/default/disable_ipv6` применяется к новым interfaces: [ip-sysctl documentation](https://github.com/torvalds/linux/blob/master/Documentation/networking/ip-sysctl.rst). Изменения выполняются после создания sandbox netns и не затрагивают host settings.
- Если совместимый pasta выбран, но его setup завершается ошибкой до release gate, direct mode пробует заранее проверенный slirp backend. Переход разрешён только при поддержке IPv4 host forwards и IPv4 DNS. Pasta сначала останавливается, чтобы освободить созданные им host sockets. Если slirp тоже не готов, запуск остаётся fail-closed; после старта приложения backend не меняется.
- Resolver для такого fallback монтируется read-only с адресами обоих backend. Одинаковые адреса дедуплицируются; при разных адресах fallback nameserver включается после primary, с `timeout:1 attempts:1`, чтобы приложению не требовалось перемонтировать resolver после выбора backend.
- `direct` отключает автоматические host публикации в обоих направлениях. Pasta получает `--tcp-ns=none`/`--udp-ns=none` и отдельные `--tcp-ports`/`--udp-ports`; slirp не открывает host forwards до явных `add_hostfwd` запросов. API slirp принимает IPv4 host address и один порт на запрос, поэтому диапазоны разворачиваются в последовательность запросов; ошибка любого правила отменяет запуск.
- Direct DNS содержится в read-only `/etc/resolv.conf`, созданном через bwrap `--ro-bind-data`. Host IPv6 nameservers отбрасываются; если не осталось IPv4 DNS, запуск завершается ошибкой. Для pasta IPv4 loopback resolvers переводятся в `--dns-forward`/`--dns-host`; для slirp используется встроенный `10.0.2.3`, если DNS не переопределён профилем. Источники: [pasta manual](https://passt.top/builds/latest/web/passt.1.html), [slirp4netns API/manual](https://github.com/rootless-containers/slirp4netns/blob/master/slirp4netns.1.md).
- PID-файл pasta — обязательный readiness сигнал; без него gate не открывается. Если доступны `/proc/<pid>/fd` и `/proc/<pid>/net`, isobox дополнительно сопоставляет endpoint-ы с сокетами pasta и учитывает native endianness Linux ABI. Slirp port rules разворачиваются в отдельные запросы `add_hostfwd`; их сериализация и fail-closed разбор API-ответа покрыты unit-тестами. Реальный slirp API socket и TCP/UDP host-forward путь проверены live acceptance harness.
- Egress guard: проверенный в preflight абсолютный путь к `nft` передаётся helper-процессу; он создаёт таблицу `inet isobox` внутри новой network namespace до запуска приложения. Вход и output имеют `policy drop`; loopback и established разрешены, новые входящие TCP/UDP — только на указанные профильные порты. Forward policy — drop. Если nft не применяет полный набор правил, helper завершается до запуска приложения.
- Порядок полномочий: bwrap даёт helper-у `CAP_SYS_ADMIN` и `CAP_NET_ADMIN` только внутри rootless user namespace. Helper устанавливает `no_new_privs`, создаёт новый network namespace, сбрасывает `CAP_SYS_ADMIN`, передаёт `CAP_NET_ADMIN` только процессу nft, после применения правил сбрасывает все capability sets и устанавливает seccomp-ограничение на namespace syscalls. Приложение запускается без capabilities. Для профилей без опубликованных портов bwrap напрямую использует `--disable-userns` и `--assert-userns-disabled`.
- Стартовый барьер: direct и off+ports helper ждут на временном Unix socket, смонтированном read-only в `/run`. Supervisor проверяет peer credentials и находит host TID потока в изолированном netns; для direct затем подключает pasta/slirp, для off+ports ставит nftables и подключает pasta. При ошибке IPv6 sysctl, helper, backend или startup gate приложение не запускается; при неожиданном выходе backend работа приложения прекращается.
- Для off+ports требуется установленный `nft`; его бинарный файл должен быть доступен в стандартном rootfs, который подключает isobox. Правила строятся только из проверенных числовых портов; host bind address применяется только в аргументах pasta.
- Настройки `network <interface> <IPv4 CIDR> { ... }` относятся к `direct`, `proxy` и `egress`; отсутствие значений сохраняет прежние имена и адреса. CIDR может быть первым позиционным атрибутом без имени. При CIDR случайно выбирается адрес из host-части подсети; `direct` через pasta также случайно выбирает отличный gateway в той же подсети. В proxy/egress guest, DNS и host-gateway endpoints выбираются раздельно из этой подсети. Пользовательская direct-сеть требует pasta и не использует slirp fallback, так как slirp назначает собственный guest IP.
- Seccomp сейчас принимает native ABI amd64, arm64, 386, arm, ppc64/ppc64le, s390x и riscv64. Для другого Linux ABI запуск off+ports блокируется. `clone3` возвращает `ENOSYS`, чтобы runtime при наличии fallback мог использовать `clone`; совместимость приложений без такого fallback требует runtime acceptance.
- Live acceptance для `off` без портов подтвердила отказ host-loopback TCP, внешних TCP/UDP и DNS. Итоговая `pasta_off_acceptance.py` для `off` с портами подтвердила блокировку host/Internet TCP, UDP/DNS, невозможность создать ICMP datagram socket, работу host TCP/UDP на объявленном порту и отказ на не объявленном порту. Ранние nft/pasta failures и их причины описаны в `QA.md`; они устранены поздним созданием network namespace после bwrap mounts.
- `pasta --help` обрезан на 4096 байтах, поэтому скрытые capability flags проверяются parser probes. Runtime acceptance direct проверяет IPv4 на pasta и slirp, DNS override, forwarding, пустой `/proc/net/if_inet6`, нулевые application capability sets и отсутствие внешнего IPv6 трафика. Сценарии сохранены в `source/slirp_acceptance.py`; off-mode port acceptance — в `source/pasta_off_acceptance.py`.
- Direct runtime fallback между pasta/slirp проверяет только заранее подтверждённо совместимые IPv4 профили. IPv6 DNS и host forwarding отклоняются валидацией профиля.
- Runtime сравнение pasta/slirp для IPv4 и off-mode firewall/ingress acceptance подтверждены. IPv6 sysctl применяется внутри netns, отсутствие IPv6 адресов проверено live на pasta, slirp, fallback и off. Если sysctl нельзя изменить/проверить, helper не запускает приложение; если pasta не поддерживает `--ipv4-only`, preflight завершает direct/off+ports fail-closed.
- Дополнительный источник для startup gate и capabilities: [bubblewrap manual](https://github.com/containers/bubblewrap/blob/main/bwrap.xml).
